# go2lean: Lean finds the inputs, `go test` is the judge

*2026-11 · [go2lean](../../README.md)*

Most Go bugs that reach users are not exotic. A slice is indexed with
an offset nobody checked. A nil slips through an API. An integer wraps
around. A goroutine waits on a channel nobody will ever write to. Fuzzers
find some of them, static analysers flag some others, and code review
catches the rest when the reviewer happens to look in the right place.

go2lean takes a different route. It translates a Go package into an
executable model written in [Lean 4](https://lean-lang.org/), searches
that model for an input that breaks a property, and then hands the input
back to Go: every candidate is replayed as a real `go test`, and only a
failure Go itself reproduces is reported as a finding. Lean finds the
inputs; `go test` is the judge.

This post explains what go2lean finds, how it works, why it is built
this way, and what happened when we pointed it at grpc-go.

## What a finding looks like

You run one command in a Go module:

```sh
go install github.com/fooexec/go2lean/cmd/go2lean@latest
go2lean run ./...
```

No spec is needed to start. For every exported function and method,
go2lean generates a `no_panic` property: *no input makes this panic*. A
function with a loop also gets `no_hang`: *no run comes back to a state it
was in*. The run ends with a summary that leads with what matters, the
panics a caller can reach, each with a runnable test:

```text
## Confirmed, tier 1: a caller can pass this input

### cx_github_com_google_btree_newfreelist_nopanic
- property: NewFreeList does not panic on any input
- inputs: size = -1
- real: panic: runtime error: makeslice: cap out of range
- PoC: out/poc/cx_github_com_google_btree_newfreelist_nopanic/
```

The PoC directory is a `go test` you can run, read and paste into a bug
report. Each finding is also ranked:
- **tier 1**: a caller can pass this input;
- **tier 2**: it depends on what callers do;
- **tier 3**: it rests on a value the API never builds itself;
- **tier 4**: it rests on an input the test had to forge.

You read the top of the list first.

Panics are only the start. A business rule is an ordinary Go function:

```go
// go2lean:spec Sum
func SpecSum(xs []int, ret int) bool {
    for _, x := range xs {
        if x < 0 {
            return true // only constrains non-negative inputs
        }
    }
    return ret >= 0
}
```

go2lean compiles the spec into the model with the target and searches
for inputs that make it false: here, an overflow, which never panics and
so no panic check would see. The same Go function is then the oracle when
the input is replayed in Go. For concurrent code, the properties are
deadlocks, goroutine leaks and data races, with the model's schedule
replayed in Go when Go's own scheduler does not take it.

## How it works

![The go2lean pipeline](../images/how-it-works.svg)

The pipeline has three stages.

**1. The compile stage: Go to a Lean model.** go2lean lowers the package
with `golang.org/x/tools/go/ssa` and translates each SSA function into a
term of a small Lean language: blocks, one operation per instruction, a
heap, goroutines and channels. A total interpreter written in Lean, with
fuel, runs it. The dependencies the code calls are translated the same
way. So is most of the standard library that is plain Go: `strings`,
`strconv`, `math/big`, `slices`, `compress/*`, the encodings and more.
What the model cannot follow is not guessed. A call into the OS, an
unmodelled `reflect` method or an assembly routine becomes **havoc**, an
explicit unknown, and every run records which havoc it read.

**2. The spec & search stage: looking for a counterexample.** Lean
evaluates the model directly; nothing is symbolic. Two engines search it:
- a **random engine**, seeded and steered by the constants in the code
  (the `"\r\n"` a parser compares against, the `16` a buffer is sized
  by), runs thousands of trials;
- an **exhaustive engine** enumerates small domains completely. When it
  finds nothing, the property holds for that bounded domain, and the
  summary says so.

For concurrent harnesses, the search also explores schedules.

**3. The replay stage: the real Go toolchain decides.** Each
counterexample becomes a Go test that builds the same inputs, calls the
real function and checks the same property. It runs under `go test` in a
sandbox, with `-race` for concurrent code. There are three verdicts:
- **confirmed**: Go fails the same way;
- **spurious**: Go does not fail. The summary names the havoc or
  assumption the model's run rested on, which is the gap to close;
- **inconclusive**: the replay could not decide.

When a spurious verdict comes from a dependency call the model skipped,
go2lean translates that call and searches again.

## Why it is built this way

**Why a model at all, and not just a fuzzer?** The model sees everything.
It knows the constants the code compares against, it can enumerate a small
domain exhaustively, and it can pick the schedule of every goroutine. A
fuzzer is blind to all three. A model also opens the second half of the
loop: when no counterexample exists, the same model is what `go2lean prove`
proves properties of, for every input, and Lean's kernel checks the proof.

**Why Lean?** It is one language for three jobs:
- an executable semantics, fast enough to run millions of steps in a
  search;
- the place the properties are stated;
- a proof checker trusted by mathematicians.

The model's semantics is written down once, in Lean, and tested against
Go on Goose's semantics corpus and our own: 292 programs, each run in both
and compared.

**Why replay everything?** Because a model is never the program. Every
gap in the translation is a place where the model can do something Go
never would. go2lean's rule is that the model may over-approximate (havoc
instead of a guess) but a finding must be reproduced by Go. You never read
a "bug" that only exists in the model. A spurious verdict is still useful:
it names its cause, and it is how we find what to model next.

**Why say what was not checked?** A bounded search is not a proof, and
go2lean says so. A property is reported as:
- **exhausted** when the search covered its domain with nothing assumed;
- **exhausted_assuming** when it rested on havoc or an assumption;
- **proved** only when Lean's comparator accepted a proof against
  go2lean's own statement of the property.

## Specs written by an agent

A `no_panic` template finds what crashes. It cannot find a parser that
accepts what its grammar forbids, a matcher that says no where it should
say yes, or an error message that names the wrong problem. Nothing
crashes there, so neither a panic check nor `-race` sees it. For that
you need an oracle: a statement of what the right answer is. That is
what a spec is, and writing specs is a job an LLM agent does well.

`go2lean agent` runs that loop:

1. **Propose.** The agent reads the package, its documentation and
   go2lean's model report, and writes specs as ordinary Go:
   - a `go2lean:spec` for one function's result;
   - a `go2lean:sequence` for what must hold over a series of calls.
2. **Repair.** go2lean compiles the specs into the model. A spec that does
   not compile, or that fails on the package's own examples, goes back to
   the agent with the error.
3. **Search.** go2lean searches every spec, then hands each one to
   `go test -fuzz` as well. A spec is a Go function, so both tools can run
   it.
4. **Report.** Each violation is replayed, and the agent reads the
   confirmed ones against the documentation: a bug, a design choice, or a
   wrong spec. Its report can revise the specs, which starts another
   round.

This is one of the specs the agent wrote for
[gobwas/glob](../eval/glob.md)'s lexer, taken from the documentation of
its error tokens:

```go
// go2lean:sequence Lexer.Next
// SeqInvalidUTF8IsReported: a pattern whose only problem is an invalid
// UTF-8 byte yields the Error "invalid UTF-8 sequence", not a later
// follow-on error.
func SeqInvalidUTF8IsReported(events []byte, inClass bool) bool {
	// ... build a pattern from events with one invalid byte at the end ...
	l := NewLexer(string(p))
	for i := 0; i <= len(p)+1; i++ {
		if t := l.Next(); t.Type == Error {
			return t.Data == "invalid UTF-8 sequence"
		}
	}
	return true
}
```

go2lean's search found a counterexample, and `go test` confirmed it.
`"\\\xff"` reports "trailing backslash", and `"[\xff"` reports
"unexpected end of input": the lexer overwrites its first error with a
later one.

Over two rounds on glob's two packages, with four LLM calls and about
eleven minutes, the agent's specs led to **6 new bugs and 1 known one**.
The templates alone found none. The spec found each bug; the searches
split the work:
- **Go's fuzzer, on the agent's specs:** an escaped `-` in a class that
  does not compile, and an invalid separator rune handled two ways.
- **go2lean's search:** a stray `}` the grammar forbids, compiled as a
  literal.
- **The agent, reading the source:** a wrong match (`*{abc,b}*c??` does
  not match `abcXc`) and the error overwrite above. Its specs then
  pinned each one down.

For a concurrent program, a spec states what a `-race` run cannot check:
that a cache never returns an evicted value, or that a counter ends at
the number of increments.

In Claude Code, the repository's
[go2lean-spec skill](../../.claude/skills/go2lean-spec/SKILL.md) gives an
agent the same method:
- which functions to check, and with which oracle (a documented contract,
  a reference implementation, a round trip, an invariant);
- how to write the spec;
- how to read each verdict.

## What it has found

go2lean is developed by running it on code it has never seen, with a
protocol fixed in advance and the tool frozen during each run. Everything
below is in the repository with its data.

- **35 open-source projects, in five runs**
  ([first](../eval/first-run.md) to [fifth](../eval/fifth-run.md)).
  Among them are chi, msgpack, go-toml, logrus, goldmark, gorilla/websocket,
  groupcache, btree, go-version, pkg/errors, lo, uuid and cron. Most runs
  finish in minutes. The findings are confirmed panics with PoCs: indices
  taken from the caller without a bounds check, nil dereferences, negative
  sizes, documented `Must*` panics, goroutines leaked by a writer the caller
  never closes. On the fifth run's seven projects, five gave no spurious
  verdict on the first try. After fixing the gaps the other two showed,
  none of the seven does.
- **Concurrency, on [GoKer](../concurrency.md#goker)**: 103 small kernels
  of real concurrency bugs from Kubernetes, etcd, gRPC, Docker and others.
  go2lean finds and confirms the bug in **60 of the 68 blocking kernels**
  (deadlocks, leaks) and **27 of the 35 non-blocking ones**, with 4
  spurious results across all 103.
- **Concurrency, on [25 recent bugs](../eval/conc-recent.md)** fixed
  since 2023 in grpc-go, sarama, prometheus, nats and containerd: go2lean
  finds 12. Go's fuzzer under `-race` finds 22 on the same harnesses, and
  go2lean found none the fuzzer missed. Each miss was a gap in the model
  around the bug, and closing those gaps took go2lean from 6 to 12.
- **[Blind spec runs](../eval/glob.md)**: on gobwas/glob, the agent's specs
  led to 6 new bugs and 1 known one, as described above.
- **The standard library**: go2lean
  [translates 74% of its functions completely](../eval/std-audit.md).
  1.8% are held back by Go constructs the model does not cover yet, and
  the rest stand on the runtime, `unsafe`, assembly and the OS.

We publish the misses too. On [29 wrong-result bugs](../eval/search-vs-fuzz.md)
taken from fix commits, with the same specs for both, go2lean's search found
7 and Go's fuzzer 11. 3 were found only by go2lean, 7 only by the fuzzer.
Where go2lean lost, the cause was a model gap on the target's path, and
each gap became an issue.

## What it does not do

- It is a **bounded search, not a verifier**. "No counterexample" is not
  "correct", except where a property is proved.
- **Havoc is honest but blunt.** Code that leans on `reflect`, `unsafe`, the
  OS or the network reaches calls the model does not follow. The search then
  rests on assumptions, and those runs give the spurious verdicts. The
  standard-library audit measures exactly how much of this remains.
- **Replay runs real code.** go2lean replays in a sandbox
  ([bubblewrap](https://github.com/containers/bubblewrap) on Linux), but
  builds run outside it. Use it on code you trust to build.

## Try it

```sh
go install github.com/fooexec/go2lean/cmd/go2lean@latest
cd your/module
go2lean doctor
go2lean run ./...
```

You need Go 1.26 and [elan](https://github.com/leanprover/elan). The Lean
toolchain is fetched on the first run. No API key is needed; the
spec-writing agent is optional. The README, the
[usage guide](../usage.md) and the [pipeline](../pipeline.md) explain
the rest. The [roadmap](https://github.com/fooexec/go2lean/issues/53) says
what comes next.
